# Rust Chess Engine — Speed, Legality and Stored-Knowledge Plan (v3)

**Audience:** your OpenCode coding agent, working inside the **existing repository**.
**Language:** Rust only (engine, tools, tests). External programs are allowed only as *offline test/analysis tools* (Stockfish, fastchess/cutechess-cli), never in the engine's runtime path.
**Priority order (from you):**

1. **Speed.** No neural network, no cloud service, no network call at move time.
2. **Never an illegal move.** Not from search, the book, the TT, tablebases, the UI/API, or a timeout.
3. **Stored knowledge used instantly.** Popular moves, underrated moves, and "leading" moves from Stockfish, Leela/AlphaZero-style engines, humans and public databases, all baked into a compact file **offline** and fetched **by the current position's hash key** during the game.

This document replaces v2. Everything in v2 is kept (merged below); new in v3 is called out in section 3.

## 5. The "no illegal moves" design

Legality is a **system property**, so it is designed in layers. Every layer must exist; any one failing must not let an illegal move out.

### 5.1 Layer 1 — One move generator, tested against an independent oracle

- The repo's movegen is the source of truth at runtime.
- In tests, **cozy-chess** (independent implementation) generates the legal move set for the same positions. Tests assert **set equality** of moves.
- Test inputs: (a) the perft suite positions at every node up to a small depth, (b) 50,000+ random playouts (seeded, reproducible) comparing the legal set after every ply, (c) hand-picked edge cases (below).

Edge cases to include (verify each against the oracle, do not trust this list blindly):

- En passant that exposes the king along a rank: `8/8/8/8/k2Pp2Q/8/8/3K4 b - d3 0 1` (the en passant capture must be illegal).
- Pinned pieces (absolute pins along files, ranks, diagonals), including a pinned pawn capturing the pinner.
- Castling: through an attacked square, out of check, into check, with rook attacked (legal), with a piece between, rights lost after rook capture.
- Promotions (all four pieces, with and without capture), promotion giving check.
- Check evasions: double check (king must move), capture the checker, block.
- Stalemate `7k/5Q2/6K1/8/8/8/8/8 b - - 0 1` (zero legal moves, not in check), checkmate, insufficient material.

### 5.2 Layer 2 — Types: `Move` is untrusted, `LegalMove` is proven

```rust
/// 16 bits: from(6) | to(6) << 6 | flags(4) << 12.  Any u16 can be wrapped, so it is NOT trusted.
#[derive(Copy, Clone, PartialEq, Eq, Debug)]
pub struct Move(pub u16);

/// Only constructible inside position.rs / movegen.rs. Holding one means "legal in the position it came from".
#[derive(Copy, Clone, PartialEq, Eq, Debug)]
pub struct LegalMove(Move);

impl LegalMove {
    pub fn get(self) -> Move { self.0 }
}

impl Position {
    /// Full check: is `raw` in the legal move list of *this* position? Used at output/UI/book boundaries.
    pub fn legalize(&self, raw: Move) -> Option<LegalMove> { /* generate legal list, find equal, wrap */ }

    /// Fast check for untrusted moves inside search (TT, killers, countermove, book hint):
    /// validates piece ownership, geometry, blockers, capture/ep/castle/promo rules. Does NOT check king safety.
    pub fn is_pseudo_legal(&self, raw: Move) -> bool { /* ... */ }
}
```

Inside the hot search, the standard pseudo-legal flow is used for speed: `make(m)` then reject if the mover's king is attacked, `unmake`. That flow is **only** allowed to see moves that came from the generator or passed `is_pseudo_legal`.

### 5.3 Layer 3 — The untrusted-move gate (every non-generator source)

| Source of a move | Why it can be wrong | Required gate |
|------------------|---------------------|---------------|
| TT best move | 16-bit/64-bit key collision, stale entry, torn read | `is_pseudo_legal`, then normal make+king check |
| Killers, countermoves, history-ordered hints | Stored for a *different* position at the same ply | `is_pseudo_legal` before use |
| Previous-iteration PV | Position differs after re-search | validate each PV move while walking it |
| Opening book | Key collision, corrupt/edited file, Polyglot castling encoding | convert encoding, then `legalize` against the **current** legal list |
| Tablebase root move | Wrapper bug, mapping error | `legalize` |
| UCI `position ... moves` / API input | Hostile or buggy client | `legalize` each move; reject with an error, do not apply |
| FEN input | Malformed, no kings, side not to move in check | validate (exactly one king each, no pawns on ranks 1/8, opponent king not capturable, castling rights consistent) |

### 5.4 Layer 4 — The output gate (last line of defence)

Every path that returns a move to the outside world goes through one function:

```rust
pub fn finalize_bestmove(pos: &Position, candidate: Move, fallback: LegalMove) -> LegalMove {
    match pos.legalize(candidate) {
        Some(m) => m,
        None => {
            debug_assert!(false, "illegal bestmove {:?} in {}", candidate, pos.to_fen());
            log_error_once(pos, candidate);   // visible in logs/metrics
            fallback
        }
    }
}
```

- `fallback` is computed **before** search starts: the first legal move (or the book/TB/depth-1 result). A timeout or abort therefore always has a legal answer.
- If the position has **no** legal moves, nothing is output; the game is over (checkmate or stalemate). The caller handles that explicitly.
- Cost: one move-list generation per move played. Negligible.

### 5.5 Layer 5 — Failure policy

- **Standalone UCI binary:** `panic = "abort"` is acceptable (fast, small); the GUI restarts it.
- **Backend service:** do **not** abort the whole server. Build with unwinding and run each search inside `std::panic::catch_unwind` (or a dedicated thread whose `join()` result is checked). On panic, log, discard that engine instance's state, and answer with the precomputed fallback legal move.
- Never `unwrap()` on anything derived from external data (book bytes, PGN, JSON, UCI text, network).

### 5.6 Layer 6 — Tests and fuzzing (gate G1, G6)

1. Perft suite exact (section 6, Phase 0) at every phase.
2. Oracle set-equality fuzz (5.1) in CI (short) and nightly (long).
3. **Search legality fuzz:** from random positions (and random playouts), run the engine at depth 1–4 and assert `bestmove ∈ oracle legal set`, including positions with exactly one legal move, in check, and with zero legal moves.
4. **Timeout fuzz:** set tiny node/time limits, assert a legal move is still returned.
5. **Book fuzz:** feed random positions + a deliberately corrupted book; assert no illegal move and no panic.
6. **TT poison test:** inject random garbage moves into TT entries; assert the search never plays or even `make`s an invalid one.
7. `debug_assert!` that incremental Zobrist key equals the from-scratch key after every `make` in tests.

### 5.7 What "no illegal moves" does **not** cover

Legal is not the same as good. A legal but weak move is a strength problem handled by search and book verification, not by this section.

### Phase 2 — Position core: make/unmake, buffers, incremental key

Why early: cloning boards to test legality is typically the biggest single cost, and the TT needs an incrementally updated key.

- One mutable `Position`. `make(m)` pushes an `UndoInfo` onto a **preallocated** stack; `unmake()` pops it. `UndoInfo` holds captured piece, castling rights, ep square, halfmove clock, previous key (and pawn key).
- `Move` packed into `u16` (flags: quiet, double push, king/queen castle, capture, ep, 4 promotions, 4 capture-promotions). `Move::NONE = 0` instead of `Option<Move>` in hot code.
- Move lists are fixed arrays on the stack (`[ScoredMove; 256]`; the known maximum legal move count is 218). No `Vec` per node.
- **Legality in search:** generate pseudo-legal, `make`, reject if own king attacked, `unmake`. Skip the test where a move cannot be illegal (not in check, not a king move, not ep, piece not pinned) once pins are tracked. Compare against full legal generation by benchmark later (Phase 10).
- Cache `king_sq[2]`. No 64-square scans to find kings.
- **Incremental key** in `make`; restore by copying the saved key in `unmake`. Updates: XOR out mover, XOR out captured piece (for ep, the real square of the captured pawn), XOR in mover or promoted piece, move the rook on castling, update castling rights, update ep contribution, toggle side.
- `debug_assert_eq!(key, compute_key_from_scratch())` after every `make` in tests and debug builds.
- Keep a key history `Vec<u64>` (capacity ≥ 1024) for repetition detection.

**Gate G2:** perft exact; bench signature identical to Phase 1; NPS up; **zero heap allocation in search** (counting global allocator test); key-from-scratch assertion green.

### Phase 3 — Polyglot Zobrist and the transposition table

**3.1 One hash scheme for everything.** Use **Polyglot's 781 constants** for the TT, repetition and the book.

- Layout: `RandomPiece[0..768]`, `RandomCastle[768..772]`, `RandomEnPassant[772..780]`, `RandomTurn[780]`.
- Piece index: `64 * kind + 8 * row + file`, row 0 = rank 1. `kind`: black pawn 0, white pawn 1, black knight 2, white knight 3, black bishop 4, white bishop 5, black rook 6, white rook 7, black queen 8, white queen 9, black king 10, white king 11.
- Castling: XOR index 768 (white short), 769 (white long), 770 (black short), 771 (black long) for each right still held (potential rights, not current legality).
- **En passant file is hashed only if a pawn of the side to move stands next to the double-pushed pawn** (capture legality is ignored).
- Turn: XOR `RandomTurn` **when White is to move**.
- Test vectors: start position `463b96181691fc9c`; after 1.e4 (`rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq e3 0 1`) `823c9b50fd114196`.

The 781 constants must come from the Polyglot specification/reference source (e.g. the `book.c`/`random` array in Polyglot or python-chess's `POLYGLOT_RANDOM_ARRAY`), checked into `zobrist.rs` as a `const [u64; 781]`. The agent must **not invent random numbers**; the two test vectors above prove the table is right.

**3.2 Table layout (Rust-sound, SMP-ready)**

Each entry is two `AtomicU64`:

```rust
#[repr(C)] pub struct TtEntry { key_xor_data: AtomicU64, data: AtomicU64 }
// data (64 bits): move:16 | score:16 | static_eval:16 | depth:8 | gen:5 + pv:1 + bound:2
// store:  data = pack(..); key_xor_data = key ^ data;  (both Relaxed)
// load:   d = data; k = key_xor_data; valid iff (k ^ d) == key   // detects torn reads and collisions
#[repr(align(64))] pub struct Cluster([TtEntry; 4]);   // 4 * 16 B = one cache line
```

- **Why:** plain shared writes from several threads are a data race (undefined behaviour in Rust). Atomics with the XOR trick are race-free and torn reads fail validation. (v2's 10-byte packed entry is only safe single-threaded.)
- Index with multiply-high: `((key as u128 * clusters as u128) >> 64) as usize` (no power-of-two requirement, no modulo).
- **Prefetch** the child cluster right after computing the child key in `make` (`core::arch::x86_64::_mm_prefetch`, behind `cfg(target_arch)`).
- Allocate zeroed memory (`alloc_zeroed`) so startup is instant and pages are touched lazily. Table size is a runtime option (MB).

**3.3 Probe and use**

1. Probe at the top of `search()` before generating moves.
2. On a valid hit:
   - Cutoff if `entry.depth >= depth`, node is **not** a PV node, and the bound allows it (exact; lower ≥ beta; upper ≤ alpha). Skip cutoffs when the halfmove clock is high (fifty-move risk) or when repetition effects may apply.
   - Always pass the TT move to the move picker **after `is_pseudo_legal`** (5.3).
   - Use the stored static eval instead of calling eval.
3. Store after the node finishes: bound (exact if alpha < score < beta, lower on fail-high, upper on fail-low), depth, best move, score, eval. Never overwrite a same-key entry's move with `NONE`. Do not store after a timeout abort.
4. **Mate scores:** store `score + ply` for winning mates, `score - ply` for losing mates; reverse on load.
5. Quiescence probes and stores too (depth 0/-1).

**3.4 Replacement and aging:** generation incremented once per `go`, never per iteration; clear the table only on new game. Replace the lowest `depth - 8 * relative_age` in the cluster; always reuse the slot with the same key. Report `hashfull` from a sample of clusters.

**3.5 Tests:** TT on/off agree on mate-in-N and tactical suites; node count at fixed depth lower with TT; mate-score round trip across plies; **TT poison test** (5.6 #6).

**Gate G3:** TT results valid; node count at fixed depth down; SPRT vs Phase 2 positive; poison test green; no data races (run the multi-thread test under `cargo +nightly miri`/ThreadSanitizer where feasible).

### Phase 4 — Staged move picker, history tables, SEE

**Stages (main search):** TT move (validated) → good captures + queen promotions (SEE ≥ 0, ordered by MVV-LVA + capture history) → killer 1, killer 2 (validated, ≠ TT move) → countermove → quiets by history (butterfly + continuation) → bad captures (SEE < 0) and underpromotions.

- The "previous PV move" is already the TT move; at the **root** order by the previous iteration's results (and node counts).
- Quiet checks are **not** a main-search stage (costly). Checks come from check extension and the first plies of quiescence.
- Generate lazily (captures first, quiets only when reached). Use pick-best selection, not full sorting.

**Tables**

| Table | Index | Update |
|-------|-------|--------|
| Killers | `[ply][2]` | quiet beta cutoff |
| Countermove | `[prev piece][prev to] → move` | quiet beta cutoff |
| Butterfly history | `[side][from][to]` | gravity update |
| Capture history | `[piece][to][captured type]` | capture cutoff/failure |
| Continuation history (1- and 2-ply) | `[prev piece][prev to][piece][to]` | quiet cutoff |

Gravity update: `h += bonus - h * abs(bonus) / MAX_HISTORY`; bonus grows with depth and is clamped; apply a malus to quiets tried earlier that failed. Lifetimes: killers per search; countermoves and histories per game (optional halving between moves); everything cleared on new game.

**SEE:** swap-list implementation first; speed up with attack bitboards if Phase 10 happens. Used for the good/bad capture split and SEE pruning.

**Diagnostics:** first-move cutoff rate (well-ordered engines cut off on the first move most of the time, often around 85–90%); a much lower rate usually indicates an ordering bug.

**Gate G4:** perft exact; SPRT positive; first-move cutoff rate recorded; every moved validated through the gate in 5.3.

### Phase 5 — Opening book runtime

**Goal:** an instant, safe lookup by the current position key. No search, no network.

**Files:** `book.rs` (runtime), asset `data/openings.obk`. Also read standard Polyglot `.bin`.

**5.1 OBK file format (own format; little-endian; header + sorted records)**

Header: magic `OBK1`, version, key-scheme id (`1` = Polyglot), record count, builder-config hash, source manifest hash + human-readable attribution text, build date, payload checksum.

Record (32 bytes, sorted by `(key, weight desc)`):

| Field | Type | Meaning |
|-------|------|---------|
| key | u64 | Polyglot position key |
| mv | u16 | from 6, to 6, promotion 3, flags 1 (engine-native encoding, castling already converted) |
| weight | u16 | derived selection weight (6.5) |
| games | u32 | human-game sample count for this move here |
| score_pm | u16 | mover's average score, permille (win 1000, draw 500) |
| over_pm | i16 | rating-adjusted over-performance, permille |
| avg_opp | u16 | average opponent rating |
| eval_cp | i16 | engine eval after the move, mover's perspective (offline) |
| eval_depth | u8 | depth of `eval_cp` (0 = unverified) |
| flags | u8 | b0 verified, b1 low-confidence, b2 underrated, b3 popular, b4 engine-best, b5 masters-backed, b6 **rejected** (never play), b7 named theory |
| first_ply | u8 | shallowest ply where seen |
| sources | u8 | bitmask: b0 Lichess games, b1 masters, b2 engine games (TCEC/CCRL), b3 Leela/AZ-style games, b4 eval dump, b5 own offline analysis, b6 imported Polyglot, b7 ECO/theory |
| eng_games | u16 | engine-vs-engine sample count (kept **separate** from human stats) |
| eng_score_pm | u16 | engine-game average score, permille |

Total 32 bytes. Human and engine statistics are never mixed into one score.

**5.2 Polyglot reader (for any `.bin` book)**

- Entry = 16 bytes: key u64, move u16, weight u16, learn u32, **big-endian** (`u64::from_be_bytes`, etc.), sorted by key.
- Move bits: to-file 0–2, to-row 3–5, from-file 6–8, from-row 9–11, promotion 12–14 (1 knight, 2 bishop, 3 rook, 4 queen). A move of 0 is ignored.
- **Castling is stored as king-takes-own-rook** (`e1h1`, `e1a1`, `e8h8`, `e8a8`). Convert to the engine's castling move (`g1`/`c1`/`g8`/`c8`) **only if the piece on the from-square is a king on e1/e8**.
- Weight in standard Polyglot books is typically `2*W + D`; the learn field is for book learning and must be left alone when you do not use it.

**5.3 Loading and lookup**

- Load once at startup (`Vec<Record>` or `memmap2`). Validate header, version, key scheme, checksum. On any failure: log, disable the book, continue with search (never panic).
- Lookup: `partition_point` on key → slice of all records for the position. Optional first-level index on the top 16 key bits.
- Read-only and shared; no locks.

**5.4 Runtime pipeline (at move time)**

1. Use the **current position's incremental key** (same key as the TT).
2. Look up all records. None → search.
3. Decode each move (convert Polyglot castling if from `.bin`) and **`legalize` it against the current position**; drop illegal or stale entries (key collisions, corrupt files).
4. Apply config filters: `ply ≤ max_ply`, `games ≥ min_games`, `weight ≥ min_weight`, not `rejected`, and (if `require_verified`) `eval_cp ≥ best_eval_in_set - eval_margin`.
5. Choose by mode (5.5).
6. Return immediately with metadata: source = Book, move, games, score, confidence, mode, source bitmask.
7. Nothing valid left → search. If `leave_on_novelty` is set and the opponent left book earlier, stop consulting the book for the rest of the game.

Lookup by key means a transposition into a known position is found regardless of move order.

**5.5 Selection modes**

| Mode | Behaviour |
|------|-----------|
| `Leading` (default) | Among verified records within `eval_margin` of the best eval: highest lead score (6.5); if nothing is verified, falls back to `Blend` |
| `MostPopular` | highest `games` |
| `BestScore` | highest Wilson lower bound of `score` |
| `WeightedRandom` | probability ∝ `weight^(1/T)` (temperature `T`) |
| `Underrated` | only records flagged underrated; weight by over-performance and confidence |
| `EngineBest` | only `engine-best` records, ties by games |
| `Blend` | `a*popularity + b*confidence + c*eval_norm`, then weighted random |
| `Deterministic` | `MostPopular`, tie-break by score, no randomness |

Randomness uses a **seeded splitmix64** (seed = game id + ply) so games are reproducible.

**Config:** `enabled, max_ply, min_games, min_weight, mode, temperature, seed, eval_margin, require_verified, leave_on_novelty, paths`.

**Gate G5:** book moves always legal (fuzz with a corrupted book); lookup by key (same entry via two move orders); missing/corrupt book falls back safely; `bench` with book off unchanged; Polyglot test vectors pass; Polyglot castling conversion test (all four).

### Phase 6 — Source ingestion and book builder (offline)

**Goal:** a deterministic, re-runnable tool that turns licensed sources into `openings.obk`. It **never** runs during play and **never** touches the network by default (downloads are separate, manual steps recorded in `sources.toml`).

**Binary:** `book-builder` (or `chess_backend/src/bin/build_book.rs`). Subcommands: `ingest-games`, `ingest-evals`, `ingest-theory`, `ingest-engine-games`, `ingest-polyglot`, `verify`, `merge`, `write`, `stats`, `check-licenses`.

**6.1 Source manifest (`data/sources.toml`)** — one entry per dataset:

```toml
[[source]]
id = "lichess-standard-2025-09"
kind = "human-games"           # human-games | masters | eval-dump | engine-games | theory | polyglot
url = "https://database.lichess.org/"
license = "CC0-1.0"
redistributable = true         # may the derived book be shipped?
attribution = ""               # text required by the license, if any
retrieved = "2026-10-12"
sha256 = "..."
```

`check-licenses` fails the release build if any source in the book has `redistributable = false` or an unknown license. A private local-only book may include such sources, but then it must be marked `private` in the header and never published.

**6.2 Pipeline**

1. **Stream, never load whole files.** zstd → PGN/JSONL line by line. Shard by file; process with `rayon`; merge.
2. **Human games** (Lichess CC0 dumps; masters if obtained legitimately): filters (min rating both players, date range, time-control class, result, termination not abandoned, minimum length, dedupe). Replay up to `max_ply` through the **canonical movegen** (SAN → move); a game with an illegal move is rejected and counted. After each move update stats for `(key_before, move)`: games, mover's result, Elo-expected score (from the rating difference), rating sums, shallowest ply.
3. **Theory names** (`lichess-org/chess-openings`, CC0: ECO, name, PGN/EPD): mark positions/moves as `named theory`.
4. **Engine games** (e.g. TCEC archive; see licensing in 7): stats go to `eng_games`/`eng_score_pm`, never into the human fields.
5. **Prune** rare entries (`games < min_games`) periodically to control memory; keep the top K moves per position (default K = 6) plus any engine-best move.
6. **Eval enrichment from the Lichess Stockfish eval dump (CC0)**:
   - Stream `lichess_db_eval.jsonl.zst`. Fields per row: `fen` (4 fields: pieces, side, castling, ep; **no move counters**), `line` (PV in UCI), `depth`, `knodes`, `cp` or `mate`. A position may have several rows with different depths: **keep the deepest**.
   - Parse FEN into a `Position` and compute the key with the **engine's** Polyglot function (do not trust the FEN's ep square for hashing; the key function applies the capture-possible rule).
   - **Only keep rows whose key is in the set of book-reachable keys** (built from steps 2–4). Do not import ~400 million positions.
   - Engine best move for a position = first move of `line` (then `legalize`; drop on failure). Candidate move eval: if the child position's key is in the dump, `eval(move) = -eval(child)`; otherwise queue for step 7.
   - **Sign convention is not stated on the dataset card.** The agent must determine whether `cp` is from White's or the side-to-move's perspective by testing on a position where one side is obviously winning, assert it in a unit test, and then normalize.
7. **Offline verification with Stockfish (external process, UCI over pipes)** for positions/candidates still without an eval, at fixed depth/nodes (default depth ≥ 20, configurable; record `eval_depth`). Run with a thread/hash budget; resumable; cache results in a local `evals.cache` keyed by `(key, move)` so reruns are free. This is where engine cost is paid, never at match time.
8. **Optional Leela/Lc0 verification** (offline, same mechanism, `sources` bit 3) if you have a network file. Runtime stays NN-free.
9. Compute `weight`, `flags`, confidence tags (6.4–6.5), mark `rejected` for moves whose verified eval is below `best - reject_margin`.
10. Write sorted, deterministic output (`key`, then `weight desc`, then `move`) with header and checksum. **Two builds from identical inputs must be byte-identical.**
11. Print stats: games read/accepted/rejected(illegal), positions, records, verified count, rejected-by-eval, engine-best count, size, build time.

**Filters to expose:** GM-only, min rating, rapid/classical/blitz, recent years, results, ECO range, min games.

**6.3 Size and speed budget (so the book stays fast to load)**

Defaults: `max_ply = 24`, `min_games = 20`, top `K = 6` moves per position. After building, report records and bytes (32 B each); target a size you can load in milliseconds. Increase depth only if the lookup stays O(log n) and the file fits comfortably in RAM or is memory-mapped.

**6.4 "Popular" vs "underrated" vs "leading" (computable)**

For each `(position, move)` with human stats:

- `popularity = games_move / games_position`
- `score = score_pm / 1000`
- `confidence = wilson_lower(score, games, z = 1.96)` (small samples automatically score lower)
- `over = over_pm` (actual minus Elo-expected, which removes the bias that popular moves are played by stronger players)

```rust
fn wilson_lower(p: f64, n: f64, z: f64) -> f64 {
    if n <= 0.0 { return 0.0; }
    let z2 = z * z;
    (p + z2 / (2.0 * n) - z * ((p * (1.0 - p) + z2 / (4.0 * n)) / n).sqrt()) / (1.0 + z2 / n)
}
fn elo_expected(own: f64, opp: f64) -> f64 { 1.0 / (1.0 + 10f64.powf((opp - own) / 400.0)) }
```

(The Wilson bound assumes win/loss outcomes; with draws it is an approximation, which is acceptable for ranking.)

- **popular:** `popularity ≥ 0.20` and `games ≥ N_min`.
- **underrated:** `popularity ≤ 0.10`, `games ≥ N_min` (default 30; below that, tag `low-confidence` and exclude from `Underrated` mode), (`confidence ≥ position_avg_score - margin` **or** `over > 0`), `avg_opp ≥ rating_floor`, and **engine corroboration**: `eval_cp ≥ best_eval - 30` (a rarely played move with good results but a bad objective eval is not recommended).
- **engine-best:** within `engine_best_margin` (default 10 cp) of the best verified eval in that position.
- **leading:** engine-best **and** (popular **or** masters-backed **or** underrated). This is the high-confidence set: the engine agrees and humans or masters back it up.
- Confidence tags: High ≥ 200 games, Medium 30–199, Low < 30. Never describe a Low move as objectively strong in any UI text.

**6.5 Weight and lead score (defaults; tune by book-vs-book SPRT)**

```
eval_norm  = clamp(1 - (best_eval - eval_cp) / 50, 0, 1)         // 1.0 at best, 0 at 50 cp worse
lead_score = 0.30*popularity_norm + 0.25*confidence + 0.30*eval_norm
           + 0.10*masters_flag + 0.05*named_theory_flag
weight     = round(lead_score * 65535)
```

Verified moves are never ranked below an unverified one when `require_verified` is on. These coefficients are a starting point, not truth; validate by playing the engine with book A vs book B (same engine, many games, SPRT) and keep the better book.

**6.6 Tests:** replay sample games and confirm every played move within `max_ply` is found at its position; header/checksum round trip; deterministic bytes; illegal PGN moves rejected and counted; eval-dump sign-convention test; key from an eval-dump FEN equals key from replaying the moves to that position.

**Gate G6:** builder output deterministic; sample games reproduce book hits; zero illegal records (builder re-runs `legalize` on every record against a replayed position before writing); `check-licenses` passes for the shipping configuration.

### Phase 7 — Tablebases (feature `syzygy`, off by default)

**Why:** perfect endgame play and fast termination of won/drawn endings. **Cost:** disk space, and a license decision (section 2).

- Probe **WDL inside the search** when piece count ≤ N (and halfmove clock = 0 or per the prober's rules); probe **DTZ at the root** to pick moves that make progress under the fifty-move rule.
- Rust option: `shakmaty-syzygy` (GPL-3.0-or-later; probes up to 7 pieces; `Tablebase::add_directory`, `probe_wdl_after_zeroing`, `probe_dtz`; optional `mmap`). Because it works on `shakmaty` positions, a thin adapter converts the engine's `Position` to a `shakmaty::Chess` (FEN round trip is acceptable at the root and slightly costly in-search; measure).
- Alternative: Fathom (C, MIT) via FFI. This is not pure Rust; use only if you accept that and need a permissive license.
- If neither is acceptable, leave Phase 7 undone. The engine remains correct without it.
- Every tablebase move goes through `legalize` (5.3). Tablebase files are user-supplied (path option); table sizes grow sharply with piece count, so check the current sizes on the hosting site before choosing 6- or 7-man.

**Gate G7:** known won/drawn/lost endgames resolve correctly (KQK, KRK, KBNK, a few 5-man cursed-win/blessed-loss cases); with files absent the engine behaves exactly as without the feature.

### Phase 8 — Incremental evaluation

- Keep the evaluation definition; maintain inputs incrementally in `make`/`unmake`: material, piece-square (middlegame/endgame), game phase, king squares, tempo.
- **Pawn hash table** keyed by pawn key: caches pawn-structure terms and passed-pawn masks.

### Phase 9 — Search refinements and time management

Each item = its own commit + SPRT. Constants tuned on **this** engine.

1. Aspiration windows around the previous score (widen on fail).
2. Internal iterative reduction when there is no TT move at sufficient depth.
3. Reverse futility pruning (static eval far above beta, shallow, not in check).
4. Null-move pruning with zugzwang guard and verification search in endgames.
5. Late-move reductions: log-based table adjusted by history, improving flag, PV/non-PV, cut node. Never reduce captures, promotions, checks, evasions, TT move, killers, high-history moves, critical pawn pushes. Re-search at full depth when a reduced move beats alpha.
6. Late-move pruning.
7. Futility pruning (quiets, shallow, not in check).
8. SEE pruning (bad captures, losing quiets).
9. Quiescence improvements: stand-pat, delta pruning, SEE pruning, TT, all evasions in check.
10. Check extension; singular extensions only once TT data is reliable; recapture/promotion extensions only if SPRT-positive.
11. Razoring only if SPRT-positive (many modern engines drop it).
12. ProbCut last.

**Time management:** soft and hard limits per move; spend more when the best move changes or the score drops, less when it is stable and holds most of the nodes; poll the clock every ~1024–2048 nodes; book and tablebase hits return immediately.

**Gate G9:** every refinement SPRT-positive before merging; legality fuzz still green.

### Phase 10 — Board-representation gate (bitboards?)

Do not schedule a rewrite by default. After Phases 2–4, take a flamegraph:

- If movegen, attack detection, SEE or mobility dominate (rule of thumb: roughly a third or more of runtime), migrate. Otherwise fix eval/search overhead first.
- Options, cheapest first: (a) keep the current representation; (b) migrate internals to bitboards keeping a mailbox mirror during the transition, asserting both agree after every make/unmake in debug; (c) adopt an existing MIT-licensed movegen core (`cozy-chess`) behind the engine's `Position` API **only if** it benchmarks faster in `bench` (not just perft) and the API fits.
- Bitboard details: piece/color/occupancy bitboards; knight/king/pawn attack tables built at compile time (`const fn`) or by `build.rs`; sliders via precomputed magic numbers (not computed at startup), PEXT behind a build/runtime switch; direct legal generation with check/pin masks vs pseudo-legal + test: keep whichever wins in `bench`.
- Validation: perft equal, FEN round trip equal, attack-map equality vs the old implementation on random positions, make/unmake equality, Zobrist equality, bench signature equal, oracle fuzz green.

Reference points: a Rust library (`bunnies`) reports ~23M moves/thread/second on an Apple M1 versus ~120M for Stockfish; `cozy-chess` reports a 3.2-billion-node perft in ~10 s (~318M nodes/s) on the author's machine. Treat such numbers as order-of-magnitude only; they are not comparable across hardware.

**Gate G10:** only after a profile justifies it; all equality checks pass; NPS improved on `bench`.

### Phase 11 — Backend integration and Lazy SMP

**Backend**

- Long-lived engine object per active game (or a pool): reuse TT, history and book across moves.
- Run search on a dedicated blocking thread (`spawn_blocking`/worker pool), never on async runtime workers.
- Memory budget: TT size × concurrent games must fit in RAM; global cap and smaller defaults for casual games.
- Cancellation via `AtomicBool`; per-request limits on time, depth, nodes.
- `catch_unwind` + fallback legal move (5.5).
- Response: best move, source (`Book` / `Tablebase` / `Search`), depth, score, nodes, nps, PV, book metadata. **Book first, then tablebase, then search.**
- Every response passes `finalize_bestmove`.

**Lazy SMP** (only after single-thread is correct and fast)

- Threads share the atomic TT (3.2); each has its own position, stack, killers, histories.
- Light diversity between helper threads (depth/ordering offsets); main thread decides the result.
- Measure time-to-depth and **SPRT at equal time** with N threads; total nodes rise, which is expected. Keep a deterministic single-thread mode for tests and bench.
- Reference: several open Rust engines (e.g. Pounce, which also lists lockless TT, IIR, null move, RFP, LMR, aspiration windows) implement Lazy SMP; study their structure, do not copy code.

**Gate G11:** engine reused across moves; memory capped; multi-thread SPRT positive at equal time; legality fuzz green with threads enabled.

### 7.2 Practical tiering (what the book trusts, in order)

1. **Engine-verified** (eval dump, own Stockfish pass, optional Lc0 pass): decides *which moves are safe and best*.
2. **Masters / high-rated human results**: decides *which of the good moves are battle-tested*.
3. **Popularity**: decides *what is normal*.
4. **Engine-vs-engine games**: extra evidence, kept in separate fields.
5. **Names (ECO)**: labels only.

A move that is engine-best **and** battle-tested is "leading". A rarely played move that is engine-sound **and** scores well is "underrated". A popular move that the engine rejects is marked `rejected` and never played.

### 7.3 Hash-key and FEN pitfalls when merging sources

- The eval dump's FEN has **no halfmove/fullmove counters** and lists an ep square; always parse into a `Position` and use the engine's Polyglot key function.
- Polyglot hashes ep only when a capture is possible; a naive "FEN ep square → hash" gives a different key and the lookup silently misses.
- Imported Polyglot books store castling as king-takes-rook; converting wrongly yields an illegal move (caught by `legalize`, but the book entry would be wasted).

### 7.4 Tablebase prober licensing (summary)

- `shakmaty-syzygy`: pure Rust, probes up to 7 pieces, **GPL-3.0-or-later**.

Monthly Lichess dumps and the eval dump change over time. Re-run the builder with a new dated entry in `sources.toml`; the deterministic build means a diff of the book is meaningful. Never overwrite a shipped book without re-running G5/G6.

## 8. What "AlphaZero-like" can and cannot mean without a neural network

- MCTS/PUCT alone is weaker than alpha-beta for chess when you have no network to supply policy and value; the plan therefore keeps alpha-beta (Stockfish-style search).
- What is borrowed instead: AlphaZero/Leela **opening preferences** enter as stored data (Leela data under ODbL, the ~210 published AlphaZero games), verified offline, then used by key lookup.
- Correction to a common formula: `Q + c·√(ln N_parent / N_child)` is **UCB1**. AlphaZero's **PUCT** uses a prior: `Q + c · P(a) · √N_parent / (1 + N_child)`. Without a policy prior `P(a)` PUCT degenerates; this is why it is not used here.
- Noise at the root for self-play diversity is irrelevant unless you later generate training data.

## 11. Common mistakes (do not do these)

- Hashing en passant differently in the engine and the book builder (book silently misses).
- Converting Polyglot castling wrongly (king-takes-rook), or reading Polyglot as little-endian (it is big-endian).
- Trusting a TT/book/killer move without validation.
- TT cutoffs at PV nodes or near the fifty-move limit without care.
- Mate scores not ply-adjusted in the TT.
- Storing results from an aborted search.
- Clearing the TT every move instead of aging.
- Plain (non-atomic) shared TT writes under threads.
- `panic = "abort"` in a server that must keep serving.
- Judging optimizations by NPS only, or by perft only.
- Testing strength with the book on.
- Mixing human and engine-game statistics in one score.
- Importing the whole eval dump instead of only book-reachable positions.
- Assuming the eval dump's `cp` sign convention without testing.
- Bundling a dataset or book whose license is unknown (Cerebellum, ChessDB, CCRL, MillionBase) or share-alike (TCEC, Leela) without review.
- Scraping websites for moves; calling any online service from the move path.
- Running the builder or any engine verification during gameplay.
- Starting bitboards or a huge book before the TT, ordering and legality tests are solid.
